## The Problem Worth Solving

Active traders in Vietnam and crypto markets face the same three pain points:

1. **Missed signals** — Price touches a key level while the trader is away. The opportunity is gone.
2. **Alert fatigue** — Tools that fire on every tick train traders to ignore notifications. The signal-to-noise ratio collapses.
3. **Execution lag** — Even when an alert is caught in time, switching to an exchange, sizing the order, and entering manually introduces delay and emotion.

There is no widely adopted, open-architecture solution that handles all three — especially one that spans both Vietnamese domestic futures and global crypto markets in a single platform.

---

## What This Platform Does

A **real-time trading alert and automated execution system** that:

- Monitors market data continuously across multiple symbols and timeframes
- Applies 8 proven detection approaches to identify genuine entry signals — and stays silent when conditions don't warrant action
- Delivers alerts instantly to traders via multiple channels
- For cryptocurrency positions: **automatically places bracket orders on Binance Futures** — no trader action required

The system is production-deployed, running in live mode today.

## The Detection Engine: 8 Approaches

Signals are generated by a composable approach framework. Each approach is independently enabled, configured, and tested per symbol.

### TRADE Approaches — precision entry signals (5 active)
These fire when conditions meet strict multi-step validation criteria. A confirmed signal triggers notification + (for BTCUSDT-PERP) automated order placement.

| Approach | Signal Type |
|---|---|
| **STRONG_CANDLE** | High-momentum single candle breakout |
| **VRA** | Volume-reinforced approach — volume confirms price action |
| **ICHIMOKU** | Cloud-based trend and momentum detection |
| **CONSISTENT_MOMENTUM** | Sustained directional pressure across candles |
| **REVERSAL_ANCHOR_SIGNAL_CANDLE** | Reversal confirmation at structural anchors |

### ANNOUNCE Approaches — market awareness (3 active)
These fire for notable market events without requiring entry action.

| Approach | Signal Type |
|---|---|
| **LARGE_CANDLE** | Abnormally large single candle |
| **LARGE_VOLUME_CANDLE** | Volume spike with price movement |
| **PRICE_MOVEMENT** | Interval/fixed-level price crossing |

> Two additional approaches (VOLUME_SPIKE_CONFIRMATION, CONSISTENT_VOLUME_ANCHOR) are implemented and archived — available for activation without new development.

## Automated Execution: The DCA Bracket

When a TRADE signal fires for **BTCUSDT-PERP**, the system automatically places a **7-rung limit order ladder** — without any trader intervention:

```
Alert fires at price P
   ↓
System places 7 LIMIT orders at staggered prices below P (BUY) or above P (SELL)
Each order has increasing quantity — later rungs fill at better prices
   ↓
As rungs fill → average entry cost improves (Dollar-Cost Averaging)
   ↓
Take-Profit + Stop-Loss placed automatically as Binance algo conditional orders
   ↓
Bracket self-manages: TP and SL auto-update as more rungs fill
```

**Why this matters for a partner:**
- No slippage from manual entry panic
- No missed entries from delayed reaction
- Risk is pre-defined before the trade opens — every time, without exception
- Bracket runs entirely in a background daemon thread — monitoring loop is never blocked

## Validation Before Capital Risk

Every strategy can be **back-tested in REPLAY mode** against historical data before any real capital is deployed.

```
Set a historical start date → system replays market data
→ approaches execute as if live → reports generated
→ review performance → promote to LIVE mode
```

This is not a paper-trading simulation — it is a **full replay of the live execution pipeline** against real historical OHLCV data. The same code path, the same conditions, the same output format.

## Deployment & Infrastructure

The system is built for serious production workloads:

| Option | Details |
|---|---|
| **Docker** | `docker-compose.yml` · `docker-compose.production.yml` · `docker-compose.staging.yml` |
| **Kubernetes** | `kubernetes-manifests.yaml` included |
| **Cloud (Heroku / Railway)** | `Procfile` included — deploy with `git push` |
| **On-premises** | Standard Python service via Gunicorn |
| **Health check** | `GET /health` → `{"status": "ok"}` at port 8080 |

Auto-recovery is built in: if a symbol's monitoring thread crashes in live mode, a supervisor loop detects it and restarts automatically — without restarting the entire service.
